CASE 01 · ERP & CRMRelevant

ERP and CRM for Vintage Grail, a multi-branch luxury watch retailer

Inventory, consignments, pricing and sales were spread across spreadsheets, scripts, shared drives and messaging apps. Records for the same item didn't always match, and client inquiries arrived through walk-ins, web forms, social media and WhatsApp with no single client record. I ran discovery with operations and management, wrote the requirements, and built the systems that are consolidating it onto one platform.

Manila system live about ten weeks after the build started. The Hong Kong platform passed every required criterion and was adopted by staff.

  • Requirements & acceptance criteria
  • Data model
  • Role-based access
  • Build vs. buy
  • React · Express · PostgreSQL
  • Frappe/ERPNext
Read the case study

What I did

  • Ran discovery sessions and wrote the product requirements, acceptance criteria and sprint plan. Management approved them in May 2026.
  • Designed the data model, role-based access and workflow rules.
  • Built, launched and maintain the Manila system: inventory, receiving and daily counts, condition assessments, pricing decisions with reasons, sales statements and a finance export.
  • Planned and ran a time-boxed build-vs-buy test for Hong Kong and recommended the outcome.

Real incidents that shaped the design

  • A sale fell through when a client misread a complete set as incomplete, so each inclusion is now recorded separately.
  • A contract went out with the wrong model year, so documents are now generated from the item record.
  • A damaged item arrived with no condition record, so condition records are now required before shipping.

The build-vs-buy decision

A custom Hong Kong build already existed. I tested whether an open-source ERP framework could replace it: fixed timebox, fake data only, pass/fail criteria agreed in advance, a full end-to-end flow, branch isolation and field-level permissions, and hands-on testing by Hong Kong staff. Every required criterion passed, staff accepted it, and the custom build was retired. The Manila system is now moving onto the same platform.

The pattern behind it

Get every channel feeding one trustworthy record, then let pricing, stock, sales and finance read from it instead of retyping it.

CASE 02 · PRICING INTELLIGENCERelevant

AI-assisted market pricing, where AI is never the price source

Before pricing an item, a reviewer searched competitor listings by hand and shared a range in a group chat. Dealer prices, auction results and social listings were mixed together, and AI chat answers were sometimes used as a price source. I built a tool where AI collects the facts, formulas do the maths and a person makes the call.

In regular use by the pricing reviewer, client advisors and management. Every price traces back to a real listing.

  • Data pipeline
  • Validation rules
  • Google Sheets models
  • Python
  • Claude API
  • MCP server · OAuth
Read the case study

How it works

  • Identify the item against a catalogue and generate search terms.
  • An AI agent reads real listings. AI is never a price source, and every comparable keeps its link.
  • Rules for each source normalise and validate the raw text.
  • Formulas place each comparable in a tier and handle currency, landed cost and condition.
  • A person reviews and approves, and every run is saved as history.

Design decisions

  • Privacy by design: it reads only item columns, never client, consignor or payment details.
  • Fast, then full: an instant answer from sources the server can read, then a fuller check within minutes.
  • Built for non-developers: chat, a web app and a connector for the Claude app, with company-only Google sign-in.

CASE 04 · AI-DRIVEN DELIVERYRelevant

Six systems, one builder, AI agents with guardrails

In 2026 I designed and built business systems on my own by directing AI coding agents (Claude Code, Codex, Replit Agent), while keeping the requirements, data rules, testing and decisions in my own hands. I also put AI inside the products where it is reliable, with guardrails where it is not.

Six systems built in 2026: five in use and one awaiting launch, each starting from a written spec.

  • Claude Code
  • Claude API
  • Agent instructions & skills
  • Automated tests
  • Prompt-injection defence
Read the case study

How I keep AI-built software reliable

  • Requirements first: agents build against a written spec with acceptance criteria.
  • Written rules for the agent: for example, never copy client details and never let AI produce a price.
  • Reusable skills: repeatable procedures are packaged so results stay consistent.
  • Tests and acceptance: automated tests in most projects, and staff acceptance before production.
  • Human decisions: AI proposes and builds; people approve prices, go-live and access.

Guardrails I design for AI message intake

  • The model only fills a fixed schema. It can't create records, quote prices or take actions.
  • It never guesses serials, values or dates, and adds a caution when an image is hard to read.
  • It flags risks for staff, like changed bank details or requests to skip inspection.
  • It treats client messages as data, never as instructions.
Who wrote the code: I own the design, requirements, data model, rules and review. Agents write most of the code, and I test and accept it.
